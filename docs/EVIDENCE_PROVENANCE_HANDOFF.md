# Evidence integrity — validator, manifest, corrections and the alert-path replay

**Workstream:** Hermes Session 3 (physical-sensor evidence), isolated branch
`experiment/hg-v380-09-secure-camera-integration`.
**Delivered by:** the commit that introduces this file; the manifest's SHA-256 digests below are the
content-addressed reference and do not change if history is later rewritten.

Nothing in this workstream modified the release branch, activated a camera or microphone, tuned a
threshold or merged a branch. The release branch was read only.

---

## 1. Why this exists

The PR #20 review (`docs/PR20_DOC_ACCURACY_REVIEW.md`) found the release claiming "verified physical
USB sensor evidence" while every artifact that would support it lived on a different branch. A claim
like that is easy to make and tedious to disprove by hand, so the check is now a program: it resolves
each referenced artifact at the revision that is supposed to contain it and fails when the reference
cannot be satisfied.

## 2. Task 1 — the validator

`scripts/verify_evidence_provenance.py` (Python 3, standard library plus `git`; no packages).

```bash
# the release gate: strict, and fails on evidence cited by a release document but absent from it
python3 scripts/verify_evidence_provenance.py \
    --root . --manifest docs/evidence/provenance-manifest.json \
    --json-out docs/evidence/provenance-report.json

# the external branch's own CI: the same checks, but external references are expected
python3 scripts/verify_evidence_provenance.py --root . --allow-external-references

# when every referencing ref must be present locally (CI that has fetched them all)
python3 scripts/verify_evidence_provenance.py --root . --strict-refs
```

Per artifact it records exactly what was asked for: the declaring revision and its resolved commit,
the repository-relative path, whether it exists there, the content SHA-256 plus byte/line counts, the
evidence type, and whether it is release-contained or external. It fails (exit 1) on:

| failure class | meaning |
|---|---|
| `unresolved_revision` | the revision does not resolve to a commit |
| `missing_artifact` | the path does not exist at that revision |
| `empty_artifact` | the file exists but is zero bytes |
| `digest_mismatch` | a declared SHA-256 does not match the content |
| `marker_missing` | the artifact's own content does not support the declared evidence type |
| `classification_contradicted` | the content says the opposite (a "real" artifact carrying synthetic provenance) |
| `scope_mismatch` | declared release-contained but absent from the release, or declared external but present in it |
| `claim_not_supported_in_release` | a document **in the release** cites an artifact that is **not in the release** |
| `dangling_reference` | a non-release document cites an artifact absent at that revision |

A referencing revision this clone simply does not have is reported as a warning
(`references_unchecked`) rather than a failure, so a fresh clone is not falsely red; `--strict-refs`
turns it back into a failure for the release gate, where every ref must be fetched first.

Measured today, in this clone:

```
release = origin/release/hackathon-2026-mcp-candidate (df31452d)
external = origin/experiment/hg-v380-09-secure-camera-integration (f252db15)

13 artifacts declared · 12 verify against their own content · 2 release-contained · 11 external
9 failures — all claim_not_supported_in_release, from docs/SUBMISSION_PHYSICAL_SENSOR_INPUTS.md
              citing nine artifacts that are not in the release
EXIT=1
```

With `--allow-external-references` — the correct setting when validating the external branch — the
same tree exits 0. So the tool distinguishes the two situations rather than flagging both.

## 3. Machine-readable evidence manifest

`docs/evidence/provenance-manifest.json` (schema `hg-evidence-manifest/1`) declares each artifact:
`id`, `path`, `revision`, `scope` (`release` | `external`), `evidence_type`
(`real` | `synthetic` | `transcribed`, plus `documentation` and `implementation` for artifacts that
carry no measurement of their own), optional `content_markers` / `forbid_markers` / `sha256`, and a
`referenced_by` list naming the documents that cite it. Types are not taken on trust: the validator
requires a `real` artifact to carry a provenance label, a `transcribed` artifact to say it is a
transcription, and a `synthetic` artifact to carry a synthetic marker — and rejects the opposite
marker if present.

`docs/evidence/provenance-report.json` is the generated report (schema `hg-evidence-report/1`): the
resolved refs and commits, per-artifact facts, the `referenced_by` confirmation for each citation, the
`references_unchecked` list, and the findings. It is regenerated by the command above.

The copy committed here was produced with `--allow-external-references`, which is the correct
mode for this branch and exits 0. Run without that flag — as the release gate does — and the
same tree reports the nine `claim_not_supported_in_release` findings printed in §2.

## 4. Task 2 — tests

`tests/scripts/test_evidence_provenance.py` — 16 tests, standard-library `unittest`, no packages.
Each builds a throwaway git repository with a `release` and an `external` branch, so the validator is
exercised against real commits rather than mocks.

```
python3 -m unittest discover -s tests/scripts -v      →  Ran 16 tests ... OK
ctest --test-dir build -R evidence_provenance         →  2/2 passed
```

| required case | test |
|---|---|
| valid committed artifact | `test_valid_committed_artifact_passes` (+ `..._with_its_marker_is_accepted`, `..._must_say_so`) |
| missing artifact | `test_missing_artifact_fails` |
| wrong git revision | `test_unresolvable_revision_fails`, `test_file_absent_at_the_declared_earlier_revision_fails` |
| valid external-branch reference | `test_valid_external_branch_reference_passes` |
| incorrect real/synthetic classification | `test_real_artifact_carrying_synthetic_provenance_is_rejected`, `test_synthetic_artifact_without_a_synthetic_marker_is_rejected` |

Plus the two cases the tool exists for: `test_release_document_citing_absent_external_evidence_fails`
(and its `--allow-external-references` counterpart), `test_reference_token_must_actually_appear_in_the_citing_document`,
`test_declared_digest_mismatch_fails`, `test_empty_artifact_fails`,
`test_declared_release_scope_that_is_actually_absent_fails`,
`test_referencing_revision_absent_from_the_clone_warns_unless_strict`, and
`test_report_is_machine_readable_and_counts_evidence_types`.

Both are registered with CTest in the top-level `CMakeLists.txt`, guarded by `find_program(python3)`,
so `ctest` covers them alongside the C++ suite.

## 7. The unverified alert path, investigated with recorded scalars only

`tests/core/test_camera_replay.cpp` (`[camera][replay]`, 5 cases / 253 assertions) replays the six
confirmed sustained-increase observations from the consented capture — typed in exactly as the
committed capture log printed them — through the **real** `DetectionFusionRule` and the **real**
`FusionEngine`. Every replayed observation is labelled `Provenance::synthetic`, because a replay is not
a measurement, and a test asserts that label cannot slip.

**This is not a physical end-to-end result and is not reported as one.**

| replay | fused verdict | confidence | alert |
|---|---|---|---|
| the six recorded rises, alone in a window | detected | **0.6965** | fires, severity `info` |
| …plus one quiet observation | detected | **0.5117** | fires (margin ≈ 0.012) |
| …plus two quiet observations | detected | **0.3918** | **suppressed** |
| the recorded 600-frame run as a whole (47 detected / 68 not_detected / 3 inconclusive = 115 votes) | **inconclusive** | **0.0415** | **suppressed** |
| the recorded still-scene composition (0 increases) | not_detected | 0.0237 | suppressed |

The headline is the fourth row, and it is not the number anyone expected. The recorded run does not
fail the *confidence* gate; it fails the engine's **agreement** threshold. The 41 settling decreases
are confirmed changes too, so they vote "detected" beside the 6 rises (47 positive) while the 68 quiet
observations vote "not_detected" — agreement 68/115 = **0.5913** against a 0.6 threshold, so the fusion
reports *inconclusive* and no alert can be raised from it.

Consequences worth carrying into the submission, the roadmap and any merge decision:

1. **The blocker is the vote mix, not the sensitivity.** Lowering the confidence gate would change
   nothing here; the agreement rule fires first. This is the measured form of the dilution analysis in
   `docs/PHYSICAL_CAMERA_PATH.md` §10.3.
2. **Cadence is the control that matters.** FusionEngine's window is 60 s by default and the recorded
   observations arrive at ~2.8/s, so a window accumulates ~115 votes for a ~2-second event. Emitting
   one observation per *second* rather than per 5 frames, or narrowing the window, is the lever — and
   it must be a documented configuration choice, not a threshold nudge.
3. **A camera-triggered alert is therefore still unproven, with a reason** — and that reason is
   reproducible in five tests rather than asserted in prose.
4. **Before any merge**, `DetectionFusionRule.cpp`'s hard-coded `{"provenance", "synthetic"}` alert
   detail must become derived, or a real-camera-driven alert would carry a false provenance field.
